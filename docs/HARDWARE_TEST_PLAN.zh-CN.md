# 硬件测试计划 — 上电调试阶段 A…O

[English](HARDWARE_TEST_PLAN.md) · **中文**

供第一次拥有真实板子时使用。每个阶段都说明要接什么、要输入或按下什么、通过是什么样子
的，以及不通过时最可能的原因是什么。每个阶段都有一个**仅软件的兜底方案**，因此缺少示波
器或信号发生器永远不会把上电调试完全阻塞住。

顺序很重要：A→B 确立任何东西到底有没有在运行；C→E 证明用户界面；F→H 证明模拟输入；
I→K 证明算法；L→N 证明链路与记录。不要从 I 开始。

安全第一：**绝不可把电极直接接到 PA0 上。** PA0 期望的是一个调理电路的输出。在阶段 H
完成、并且它的输出摆幅被测量出来之前，驱动 PA0 只能用信号发生器或电位器分压，不能用一
个人来驱动。

---

## 阶段 A — 它到底能不能启动

**接线。** ST-Link 接到 SWD（PA13 SWDIO、PA14 SWCLK、GND、3.3 V）。其余什么都不接。
**操作。** 烧录 `MDK-ARM/Human Heart and Body Temperature Monitor/<name>.hex`，复位，
挂上调试器并暂停一次；然后运行并再次暂停。
**通过。** 两次暂停时程序计数器都在 `App_Loop()`（或它调用的某个函数）内部，
并且 `ecg_signal.c` 中的 `s_sample_index` 单调递增。
**软件兜底。** 没有调试器时，暂停并查看是做不到的：直接去做阶段 L 并读取 UART，它在
STATUS 包里报告 `adc_running`、`ecg_samples` 和 `uptime_seconds`。会变的
`uptime_seconds` 就是启动的证据。
**诊断。**
- 卡在 `Error_Handler()`（`__disable_irq(); while(1);`）→ 某个 `MX_*_Init()` 或
  `SystemClock_Config()` 失败了；几乎总是 HSE 或 LSE，所以下一步做阶段 B。注意
  `Error_Handler` 是在任何输出都还可能产生*之前*就被到达的，所以时钟死了在 UART 上同样
  看不见。
- `ecg_samples` 一直停在 0 → 阶段 F/G。
- 能运行但 `uptime_seconds` 从不前进 → 检查 `uwTick` 是否在递增，也就是 SysTick。

## 阶段 B — HSE 与 LSE 真的在振荡

**操作。** 挂上调试器，运行 5 s，暂停，查看 `RCC->CR`。
**通过。** `HSEORDY`（第 17 位）= 1 且 `LSEORDY`（第 1 位）= 1；`PLLORDY` = 1；
`RCC->CFGR` 显示 `SWS = 10`（PLL 作为 SYSCLK）。通过读取 `SystemCoreClock`
= 72000000 来确认内核时钟。
**软件兜底。** 在 `Error_Handler` 里设一个断点，看它是否被命中；或者观察
`rtc_service_is_valid()` 是否会变为真，以及在写入一个时间之后 STATUS 包的 `RTC` 字段是
否说 `SET` 而不是 `UNSET`（没有 LSE 的 RTC 不会前进）。
**诊断。**
- HSE 未就绪 → 晶振负载电容不对、晶振缺失，或者使能动作在与未被映射的 PD0/PD1 较劲。
  HSE_VALUE 必须是 8 MHz（`stm32f1xx_hal_conf.h`）。
- LSE 未就绪 → 32.768 kHz 晶振缺失或被过驱动。**后果是严重的，而且这是有意设计的：**
  `SystemClock_Config()` 会调用 `Error_Handler()`，所以即使除 RTC 之外的一切都能工作，
  板子看起来也是死的。如果装上 LSE 之前必须继续上电调试，那属于一项 CubeMX 改动（把
  RTC 源改为 LSI 或 HSE 分频），并且必须经由 `.ioc` 完成，而不是去编辑 `main.c`。
- HSE 就绪但 `SWS != 10` → PLL 配置；检查 `PLLMUL = ×9` 与 `PLLSRC = HSE`。

## 阶段 C — 三个按键

**接线。** PB12、PB13、PB14 各自通过一个瞬时触点接到 GND。内部上拉已由冻结的配置使能。
**操作。** 按下之后在 `buttons_scan()` 内暂停，或者干脆前进到 STATUS 页并按下每个键，
看着 `uart_rx_packets`/高亮的菜单行移动。
**通过。** UP 把高亮向上移，DOWN 向下移，OK 进入。一次按下只登记一次，而不是四次。
**通过 — KEY_OK 专项（由 Phase 1 评审修复加入，目前尚未执行）。** 在 ECG 页上，OK 必须
开始录制并打开 PC 端流式传输；再按一次以停止。然后导航到 SETTINGS，或 DATE & TIME，并在
任意条目上按 OK：外发的 `STATUS` 包里的 `recording` 与 `streaming` 不得改变。在该修复
之前，这个动作根本不会触发（`BTN_EVT_SHORT` 没有生产者），而页面判据会永远保持为真，
因此两个方向都从未在代码中被走过。
**软件兜底。** 不需要第二个串口：ECG 页页脚与 STATUS 页都会对按键作出反应，因此在按键
的同时，可以通过 `STATUS` 包的 UART 记录看到按键功能。
**诊断。**
- 行为反转（高亮在松开时移动）→ 板子被接成了高电平有效到 3V3，而不是低电平有效到 GND。
  在 `App/buttons/buttons.c` 的 `read_raw()` 里修，一行，并更新 `docs/PINMAP.md`。
- 一次按下产生多个事件 → 对这些开关来说 `DEBOUNCE_MS` 太小；调大它。
- 完全没反应 → 确认 `gpio.c` 仍在 PB12/13/14 上设置 `GPIO_PULLUP`（在冻结的基线里确实
  如此），然后检查该引脚没有被短路到某个电源轨，内部约 40 kΩ 的上拉是斗不过电源轨的。

## 阶段 D — 找到面板

**操作。** 把模块经 I2C1 上电（PB6 SCL、PB7 SDA、3V3、GND）。复位 MCU。挂上调试器并
查看 `oled_bus_address_8bit`、`oled_bus_scanned`、`oled_present`。
**通过。** `oled_bus_scanned == 1` 且 `oled_bus_address_8bit` 是 `0x78` (0x3C<<1) 或
`0x7A` (0x3D<<1)。
**实测于 2026-09-19 — 在第一块板子上 PASS。** 在模块供电约 3.3 V、PB6/PB7 空闲在约 3.3 V
的情况下，调试器显示 `oled_bus_scanned = 1` 且 `oled_bus_address_8bit = 0x78`，也就是 7 位
`0x3C`。用户把模块上的器件认定为 **SSD1306**，于是配置档和地址现在两者都是观察所得而非
假设。`0x3D` 从来就不需要。
**软件兜底。** `HELLO` 与 `STATUS` 包携带 `oled_address` 和 `oled_present`，因此完全没有
调试器时也能通过串口链路读到该地址。
**找到地址并不能告诉你*什么*。** 关于控制器、它的列偏移、它的分辨率，或者该地址是按 7 位
还是 8 位表示 — 一无所知。上游自己的移植说明禁止用某个常见默认值去填这些空缺，本计划遵循
这一点：先从器件的丝印或软排线印刷、或从厂商产品页识别出具体型号，然后才去挑一个配置档。
**诊断。**
- 没有地址应答 → 检查 3V3/GND，以及 SCL/SDA 上是否存在外部上拉（开漏不会自偏置）。在
  SCL 上用示波器看 100 Hz 是快速检查法；没有示波器时，HAL 返回 `OLED_ERROR` 且
  `oled_present` 保持为 false，这是同一个信号。
- 在 0x3C 有应答但面板是黑的 → 阶段 E。

## 阶段 E — 像素，以及选择控制器配置档

**操作。** 根据模块上的标记选定配置档，把 `OLED_CONTROLLER_SELECTED`
（`SSD1306`、`SH1106` 或 `CH1116`）设为一个编译器宏定义，重新编译、烧录、复位。
**通过。** MAIN 菜单清晰可读、居中、没有水平偏移、没有镜像、没有在分页边界之间出现垂直
拖影。
**实测于 2026-09-19 — PASS，在修好了描述符生命周期的那个构建上。** 烧录
`fix/ui-app-lifetime` 之后，面板显示的是 **MAIN 菜单，文字居中且没有水平偏移**，没有镜像，
也没有在分页边界之间出现拖影。这就了结了那两桩全白帧无法判定的事：SSD1306 配置档为 0 的
列偏移对本模块是对的，而它的 COM 扫描 / `0xDA` 配对也把每一行放在了驱动以为它们在的位置。
在这之前的黑屏是悬垂的 `KK_UI_App` 描述符，不是配置档 - 见
[KK_UI_NOTES.zh-CN.md](KK_UI_NOTES.zh-CN.md#让真实面板保持黑屏的描述符生命周期契约缺陷)。
**实测于 2026-09-19，第一次 — 像素 PASS，配置档已选定。** 一个临时的调试分支绕开 KK_UI、
直接驱动底层驱动：`OLED_Init()` 在 SSD1306 配置档上返回 OK，而一次整帧的 `OLED_Fill()` +
`OLED_Update()` 点亮了 128×64 玻璃上的**每一个像素**。于是总线、包含 `0x8D,0x14` 的初始化
块、分页寻址以及 `0xAF` 全都确认于硬件之上，下面表格里"完全黑屏但 I2C 有应答"那一行对本
模块已被排除。
**那一帧没能定下什么、又定下了什么。** 一个全白帧无法揭示列偏移或 COM 排布 —— 每种映射下
都是白的，所以那个图案步骤仍然欠着。上面所描述的居中的 MAIN 菜单就是把它付清的东西：由
同一批参数摆放的文字出现在驱动意图的位置上。（`debug/oled-bringup` 分支还带有
`OLED_BRINGUP_PATTERN_CHECKER` 与 `_BORDER`，万一想要对边缘做一次更精确的测量的话。）
**以及修复之前菜单为什么是黑的。** 冻结的那份固件在有 ACK 的情况下依然什么都不显示，因为
`ui_app_init()` 交给 `KK_UI_Init()` 的是一个栈局部描述符的地址，而 KK_UI 在每一帧上都继续
使用它。见
[KK_UI_NOTES.zh-CN.md](KK_UI_NOTES.zh-CN.md#让真实面板保持黑屏的描述符生命周期契约缺陷)；
修复是 `fix/ui-app-lifetime`。
**症状 → 配置档改动。**
| 症状 | 含义 |
| --- | --- |
| 内容右移 2 px | 面板是 128 列（SSD1306），但选中的是一个 132 列、列偏移 2 的配置档：切换到 `OLED_CTRL_SSD1306`，它使用偏移 0 |
| 内容左移 / 最左边 2 列缺失 | 真实面板是 SH1106 一类：使用 `OLED_CTRL_SH1106`，偏移 2 |
| 右半显示左半的内容、重复出现 | 分页寻址不匹配 — 确认该配置档发出 `0x20,0x02` |
| 每一行都反色（暗 ↔ 亮） | `0xA6` / `0xA7` 配对；在该配置档里对调它 |
| 各行以错乱的顺序出现 | COM 扫描方向：`0xC0` 与 `0xC8`，以及 COM 引脚排布 `0xDA` |
| 完全黑屏但 I2C 有应答 | 电荷泵：SSD1306 需要 `0x8D,0x14`；CH1116 使用 `0xAD,0x8B,0x33`；SH1106 使用 `0x32` 或外部方案。这是面板看起来死了的最最常见原因 |
| 有显示但闪烁严重 | 该配置档里的 `0xD5` 时钟分频 / `0xD9` 预充电 |
**然后测出真实带宽**：用显示通路来测 — 向 PA0 输入一个 10 Hz 正弦，并提高频率，直到屏幕
上波形轨迹的幅度降到低频值的 0.707。这个数字是*软件*显示带宽，应写进
[CUBEMX_CONFIG.zh-CN.md](CUBEMX_CONFIG.zh-CN.md)，替换掉预测的 22.1 Hz。

## 阶段 F — ADC 输入范围与标定常数

**接线。** 信号发生器 → 经一个 1 kΩ 串联电阻到 PA0，与板子共地。信号发生器：1 Hz 三角波
或正弦，0.5 Vpp，偏置到 1.65 V。
**操作。** 流向 PC，录制 10 s，查看 `ecg_raw` 列。
**通过。** 对 1.65 V 输入，码值围绕约 2040 对称摆动，并且两端都不削顶。
**然后再推导检测门限下限。** `ECG_THRESH_ABS_MIN`（当前为 256）是从一个合成的 700 计数
R 波选出来的，那是对一个并不存在的电路的猜测。在以已知速率施加一个心搏形状输入的同时，
读出 STATUS 包送出的 `energy` 值，并把门限下限设在最强的间搏能量与最弱的真实峰值之间。
`HARDWARE TEST PLAN` 这一步：记录 energy，取 max(inter-beat) × 2 与 min(peak)/3，在该带
内选取。
**诊断。** 码值钉在 0 或 4095 → 发生器偏置错了，或者前端的输出摆幅超出了 0–3.3 V（这是一
个真实的安全与范围问题，不是软件问题）。

## 阶段 G — 采样率真的是 1000 Hz 吗

**方法 1（示波器）。** 在 `App_Loop()` 开头或 DMA 回调里翻转一个空闲 GPIO，并测量周期。
**方法 2（仅软件，不用仪器）。** 录制 30 s 并数行数：PC 由 `first_sample_index` 重建时间
轴，所以在一段实测墙钟区间上的 `last - first + 1` 就是真实速率，而 STATUS 里的
`DROP n blk` 统计设备没能及时交出的任何块。
**通过。** 1000 ± 1 Hz，零丢块。以 128 个采样为一块时，30 s 的记录应给出约 30000 个采样：
约 234 块。
**诊断。** 速率略高/略低 → LSE 精度（基于 RTC 的计时只和晶振一样准）。丢块 → 主循环被
饿死；测量 `HAL_UART_Transmit` 与 OLED 刷新加起来耗时多久，然后调小
`DIAG_STATUS_PERIOD_MS` 或 UI 帧率。

## 阶段 H — ECG 模拟前端

**这一阶段决定算法假设是否成立。**
**操作。** 接好做完的前端、并且**不接任何人**，用一个产生类心搏波形的信号发生器驱动其
输入（或者把 PC 演示流作为参考预期）。记录：输出偏置、已知输入下的输出摆幅，以及频率响应。
**填写。** `ECG_FRONTEND_GAIN`、`ECG_FRONTEND_OFFSET_MV`，把
`ECG_FRONTEND_PARAMS_VERIFIED` 置为 1。
**通过。** `mv` 列与同一测试点上的万用表/示波器一致，并且 R 波占据 ADC 范围中一个有用的
比例且不削顶。
**然后重做阶段 F。** 增益改变能量标度，而 `ECG_THRESH_ABS_MIN` 就在这个标度上。
**诊断。** R 波低于 100 计数 → 增益太低，固定的检测门限下限会漏心搏；要么提高前端增益，
要么降低门限下限。削顶 → 降低增益。偏置漂移 → 前端的偏置网络，不是软件。

## 阶段 I — 真实信号上的心率

**操作。** 在满足要求的前端和一位自愿的志愿者条件下，把设备的 HR 与受试者能给出的参考做
对比（对课程项目而言，数 30 s 的桡动脉脉搏就够了）。静息时录制 60 s，然后在轻微运动之后再录。
**通过。** 一致到你自己选定并公开声明的那个容差之内。**在你拿到支撑数据之前不要写
"±2 bpm"**；任务书禁止这样宣称。
**同时记录。** 是否有 R 波被漏检或被翻倍，以及运动期间 `SIGNAL POOR` 的比例。
**诊断。** 恒为真实心率的一半 → 每隔一个心搏就落到阈值之下：把
`ECG_THRESH_RATIO_PERCENT` 从 40 调低，或者前端增益勉强够用。心率为两倍 → T 波被检测出来
了；对这个波形来说 `ECG_REFRACTORY_SAMPLES`（250 ms）太短，或者 QRS 频带放过了太多 T 波
能量。

## 阶段 J — 温度标定

**操作。** 最终版本的传感器电路做好之后，在两个已知且已实测的温度下记录原始码值（冰水
混合物与体温温水，配一支参考温度计），并填写 `TEMP_SENSOR_MODEL` 加上
`TEMP_LINEAR_INTERCEPT_MV` / `TEMP_LINEAR_SLOPE_NV_PER_CENTI`，或者用真实曲线替换
`TemperatureConvert()`。
**通过。** 在两个点上、在 0.1 °C 的显示分辨率下，设备读数与参考在你愿意公布的那个容差内
一致。
**然后重做**探头门限 `TEMP_ADC_OPEN_THRESHOLD` / `TEMP_ADC_SHORT_THRESHOLD`：真的把探头
输入开路并短路，记录下 ADC 看到的值。
**在完成这些之前**，固件报告 `TEMP_UNCALIBRATED` 且 UI 显示 `--.-`，这是正确行为，
不是缺陷。

## 阶段 K — 导联与探头的断开行为

**操作。** 用真实前端：断开一个电极并观察。断开温度探头并观察。
**通过。** 拔掉温度探头后，在连续 `TEMP_PROBE_FAULT_CONFIRM_WINDOWS` 个故障窗口
（2 个窗口 ≈ 500 ms）之后报告 `PROBE FAULT`，并在连续
`TEMP_PROBE_OK_CONFIRM_WINDOWS` 个正常窗口（4 个窗口 ≈ 1000 ms）之后清除。单个异常窗口
绝不会在任一方向上改变指示。
**导联脱落：**除非前端提供一个本固件已接入的电极检测输出，否则设备会报告 `SIGNAL POOR`
或 `UNKNOWN`，**不是** `DISCONNECTED`，这是有意如此。要报告导联断开，需要一项本设计任何
部分都不做的测量。如果前端日后增加了这样一个输出，就需要一次 CubeMX 改动来分配一个输入，
只有到那时才应产生 `LEAD_DISCONNECTED`。

## 阶段 L — PC 链路

**接线。** USB 转串口模块接到 PA9 TX、PA10 RX、GND，与板子共地。
**操作。** `python -m pc_monitor --port COMx --baud 230400`，然后点击 Connect。
**通过。** HELLO 到达（于是连接面板显示固件与协议版本），STATUS 以约 2 Hz 跳动，发送命令
时 STATUS 页上的 `uart_rx_packets` 增加，并且 CRC 错误保持为 0。
**诊断。**
- 什么都没有 → 交换 TX/RX（最经典的那一条），或者该模块是 5 V 逻辑打到 3.3 V 引脚上。
- 先出乱码然后什么都没有 → 波特率不匹配；检查冻结的 230400。
- 偶发 CRC 错误 → 接地/电平问题；解析器按设计会重新同步，所以有诊断意义的是错误计数器，
  而不是停摆。
- 命令被接受但没有应答 → 设备只从 `App_Loop` 发送；如果它卡在某个长时间阻塞的调用里，
  那是一个真实缺陷，值得用 `DROP`/`CRC` 计数捕捉下来。

## 阶段 M — 10 s 连续录制

**操作。** 在设备上（ECG 页上的 KEY_OK）和在 PC 上开始录制，采集 60 s，停止，导出。
**通过。** `last_index - first_index + 1` 等于行数（没有间断），丢块数为 0，CRC 错误 0，
CSV 对本次会话每一毫秒有一行，并且 Excel 里的波形与屏上的波形一致。
**同时测试。** 前端能支撑的最长会话，以及在 UI 负载很重时 `DROP n blk` 的表现（ANSWER 会
告诉你阻塞式 UART TX 加上阻塞式 OLED 刷新之后是否还剩足够的余量；若不够，修法是降低 UI
速率，而不是更快的 ADC）。

## 阶段 O — 复位与断电之后的 RTC 时间连续性

**何时。** 在阶段 B 之后立刻做这一项；它不需要任何模拟硬件，只需要一块能启动的板子，以及
调试器或阶段 L 的串口链路二者之一。
**被区分开的是什么。** 这些是不同的状况，从屏幕上看起来却一模一样：
- RTC 内核没有在计数（没有 LSE，或没有 VBAT）；
- RTC 接口没有时钟：`RCC_BDCR` 的 `RTCEN`。`HAL_RCCEx_PeriphCLKConfig()` 只写
  `RTCSEL`，而 HAL 稍后在 `HAL_RTC_MspInit()` 里设置 `RTCEN`，所以在两者都还没运行之前，
  真正的冷启动就是这个样子 — 由 `rtc_clock_prepare()` 在预初始化路径上做这件事；
- 根本没有选出任何 RTC 时钟源（`RTCSEL == 0`），固件对此的处理是"不去碰任何 RTC 寄存器"；
- `RSF` 从未到来，所以 `CNTH`/`CNTL` 仍然是本次复位之前锁存的副本。在这里晶振死了与接口
  没有时钟是无法区分的，只有对照 `RCC_BDCR` 的 `LSERDY` 才分得开；
- 备份寄存器锚点缺失、撕裂，或与计数器不一致。
前四种让 `s_counter_valid` 保持清零，最后一种让 `s_anchor_available` 保持清零；每条路径
都终结于 `rtc_service_is_valid() == false`，也就是时钟报告 `UNSET`。
**操作。** 设一个已知时间，让它跑 60 s，然后 (a) 按下 NRST，(b) 在仍接有 VBAT 的情况下
断电 10 s，(c) 移除 VBAT 后断电。每一步之后都读出时间。
**通过。**
- (a) 时间保持到几秒之内 — 计数器存活下来，锚点重建成功了。
- (b) 同上，而这是 VBAT 保持在本板上确实起作用的第一个真实证据。
- (c) 时钟报告 `UNSET`，而不是一个看起来合理的错误时间。备份域丢了，锚点也就没了；猜一个
  比承认它更糟。
- (d) **冷启动**，也就是在一次故意的备份域复位之后（用调试器操作 `RCC_BDCR` 的 `BDRST`，
  或一块从未接过 VBAT 的板子）：启动必须在 `s_sync_failed == 0`、没有
  `DIAG_ERR_RTC_SYNC`、`RCC_BDCR` 显示 `RTCEN` 与 `RSF` 都已置位的情况下完成，并且用户
  随后手工设置的时间必须能挺过 (a)。在 `rtc_clock_prepare()` 之前，这个情形在一个完全
  健康的晶振下报告了 1 s 的同步超时，因为给 RTC 接口供时钟的那一位要等到
  `HAL_RTC_MspInit()` 才被写入。
**直接观察。** 暂停并查看 `rtc_service.c` 中的 `s_sync_failed`、`s_counter_valid`、
`s_anchor_available`、`s_saved_anchor` 与 `s_counter_at_boot`。通过 UART，STATUS 包只显示
后果：`rtc_valid` 标志保持清零，且 `protocol_errors` 比启动时高 1，因为
`diagnostics_note_error()` 递增那个计数器并把原因（`DIAG_ERR_RTC_SYNC`，代码 201）保存在
`last_error_code` 里，而本构建中没有任何屏幕渲染它。用调试器读出这个代码。
**诊断。**
- 一次正常复位之后 `s_sync_failed == 1` → RSF 从未到来，所以 `RTCCLK` 没有在运行。先读
  `RCC->BDCR`：到这个等待开始之时 `RTCEN` 应该已经是 1 了（那里是 0 说明使能没落地，也就是
  `DBP` 被挡住了），而 `LSERDY` 说明晶振本身是否活着。在这种状态下没有从计数器读过任何
  东西，这是有意设计。
- 锚点存在但时间往回跳 → `RTC_EPOCH_MAX_SECOND` 的拒绝没有触发，那意味着计数器并没有真的
  复位；用调试器读 `RCC->BDCR` 的 `BDRST` 历史以及 `RTC->CNTH/CNTL` 重新核查。
- (a) 之后时间是 `UNSET` 但 (b) 却能保住 → 锚点写入本身被打断了；检查
  `rtc_service_preserve()` 是否真的从 `USER CODE BEGIN RTC_Init 0` 里运行。
**未被宣称的。** 以上没有一项在硅片上执行过。重建逻辑作为纯模型是 `HOST VERIFIED`，包括对
真实写序列每一个前缀的重放；围绕它的寄存器级代码只是 `BUILD VERIFIED`。
