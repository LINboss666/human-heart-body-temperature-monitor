# KK_UI / KK_OLED 集成说明

[English](KK_UI_NOTES.md) · **中文**

记录在上游工程中实际发现了什么，以及本固件如何与之符合，这样审阅者不必自己重新推导。
出处与许可证见 [UPSTREAM.zh-CN.md](UPSTREAM.zh-CN.md)。

## 上游究竟是什么

`gitee.com/keysking/kk_ui` 并不是一个独立 C UI 库的仓库。它是一个 **Agent Skills** 发行包，
其 C 运行时是作为*技能资产*携带在 `skills/kk-ui-port/assets/kk-ui-runtime/` 下的。它无法独立
运行：每一次绘制和刷新调用都会进入 `kk_oled`，那是第二个不可或缺的仓库，它拥有帧缓冲、
图形核心以及整个硬件移植层。

两个仓库都不含示例应用、不含演示、不含 Keil 工程，也没有任何 SSD1306/SH1106 代码。
唯一随包携带的显示驱动面向 **CH1116**，挂在 `hi2c1` 上，8 位地址 `0x3D << 1`，列偏移为 2。

因此这里的集成遵循上游自己记录的流程（`skills/kk-ui-port/SKILL.md`，九个步骤，
外加 `references/porting-strategy.md` 与 `references/verification-checklist.md`）：
把运行时拷进工程，把这份拷贝视为工程自有代码，只调整驱动边界。

## 对上游契约的符合性

| 上游要求 | 本工程如何满足 |
| --- | --- |
| 应用先初始化 OLED，再初始化 KK_UI | `ui_app_init()` 在 `KK_UI_Init()` 之前调用 `OLED_Init()`；KK_UI 从不调用 `OLED_Init()` |
| `KK_UI_Update(now_ms, input)` 从单一上下文调用，至少每 10 ms 一次 | 每次 `App_Loop()` 迭代调用一次，约 5 ms；时间是传入的，没有 tick 钩子 |
| 中断只累加原始输入状态 | 按键在主循环里采样；DMA 中断不触碰任何 UI 状态 |
| 页面描述、标签、字体、图标与绑定变量在 UI 生命周期内保持有效 | **这是一次借用，而不是一次拷贝：见[描述符生命周期契约](#让真实面板保持黑屏的描述符生命周期契约缺陷)。** 其中的一切现在都是文件作用域的 `static`/`const`，包括 `KK_UI_App` 描述符本身；动态文本被格式化进静态缓冲，绝不重新绑定到临时对象。在 2026-09-19 之前，那个描述符是 `ui_app_init()` 里的一个局部变量，而这一行当时是假的 |
| 应用不得与 KK_UI 并行清屏或提交帧 | `App/` 中任何位置都不存在 `OLED_Clear()` / `OLED_Update*()` 调用；只有 `KK_UI_Invalidate()` |
| 无动态内存、无控件树、无运行时注册 | 页面是静态表；grep 确认三份代码库中分配调用为零 |
| 缺失的硬件要被报告出来，而不是猜测 | `OLED_Init()` 失败会置 `oled_present=false`，固件继续运行 |

## 偏差及其理由

1. **`KK_UI_REFRESH_MODE` = `KK_UI_REFRESH_BLOCKING`**（上游默认是 DMA）。
   DMA 刷新需要 I2C1 缓冲 DMA 及其中断向量，而被冻结的 `.ioc` 并未使能它们。增加它们就等于
   为一项仅关乎显示的好处去做一次 CubeMX 修订。代价：局部分区刷新是同步的，受脏区宽度限制；
   而双缓冲仍然被分配着，尽管没有任何内容是异步发出的。

2. **HOME 页面禁用，根页面是一个 MENU。**
   HOME 模板要求每个条目配一张 32×32 XBM（`icon_xbm_32x32` 会被校验为非 NULL）。
   为了在一块 64 KB 器件上得到装饰，而要付出编写四张图标位图、外加对它们做验证与许可证审阅
   的代价，而这些东西菜单模板本就已提供。

3. **三个槽位共用一份字体表。**
   `kk_ui_valid_fonts()` 要求 `home_font`、`title_font` 与 `body_font` 非 NULL。三者都指向
   同一个 1113 字节的数组；视觉层次来自布局和反白行。复制这张表会多花 2.2 KB flash。

4. **没有添加波形控件。**
   KK_UI 没有波形控件。`skills/kk-ui-extend/SKILL.md` 声明扩展核心是最后手段，
   且 `实现页面` 的权限并不等于 `扩展核心` 的权限，而 README 自己的指引也是把波形画在自定义
   页面里。因此 ECG 波形由 `KK_UI_CustomOnDraw()` 使用 KK_OLED 原语绘制，而
   `ThirdParty/kk_ui/src/` 与上游字节一致。

5. **在 KK_OLED 中只改动了 `driver/kk_oled_*.{c,h}`**，把三个字面量替换为从
   `App/display/oled_bus.c` 读取的值。图形核心 —— 像素排布、裁剪、双缓冲、提交状态机 ——
   未作改动，因为 `references/driver-contract.md` 把这些标为受保护边界，而
   `kk-oled-port/SKILL.md` 禁止往这些位置猜测控制器参数。

## 让真实面板保持黑屏的描述符生命周期契约缺陷

2026-09-19 在硬件上发现，对象是第一块烧录过本固件的板子。之所以把它记在这里，是因为上面
那张表里唯有这一条要求不可能靠巧合满足，也因为屏幕黑着的时候，固件里每一个状态字都在说
"没问题"。

**契约。** `KK_UI_Init(const KK_UI_App *app)` 保存的是那个指针 ——
`ThirdParty/kk_ui/src/kk_ui.c` 里的 `kk_ui.app = app;` —— 并且不会拷贝这个结构体。之后的
每一帧都透过它读取 `routes`、`menu_pages`、`info_pages`、`int_bindings`、`bool_bindings`、
`fonts` 与 `texts`。所以：

* `KK_UI_App` 对象必须比整个 KK_UI 运行时活得更久；
* 它所指的一切也必须如此：页表、条目标签、标题、行字符串、字体、绑定描述符 —— 以及绑定
  所指进去的那块存储；
* 描述符上的 `const` 是正确的，也不会冻结状态，因为绑定成员是指向可变变量的指针。一个
  `const` 描述符可以指向可变的数据。

**代码实际是怎么做的。**

```c
void ui_app_init(void)
{
    KK_UI_App app;          /* a local */
    ...
    st = KK_UI_Init(&app);  /* KK_UI keeps &app */
}                         /* app dies here */
```

**为什么什么都没检测出来。** `kk_ui_validate()` 是在那个局部变量仍然待在活动栈上时运行的，
所以 `KK_UI_Init()` 返回了 `KK_UI_OK`，`oled_present` 被置为 true，而 `last_error_code`
保持为 0。之后，`KK_UI_GetRoute()` 从此刻占据那段栈区域的任何东西里读出 `route_count`；
当这个答案没法用时，`KK_UI_DrawPage()` 提前返回，绘制缓冲与那一稳定帧完全相同，
`OLED_Update()` 发现差分为空并返回 `OLED_OK`，**而且完全不触碰总线**。每一层说的都是关于
自己的实话。面板是黑的。

**它是如何被证明的，以及在哪个层面。** 一个临时的调试分支把面板分阶段点亮，每一步都向
调试器报告：I2C 扫描 `0x3C` OK，`OLED_Init()` OK，一次直接调用的 `OLED_Fill()` +
`OLED_Update()` 点亮了**真实 128×64 模块的每一个像素**。这就把故障定在了驱动之上。随后，
出货的 `ui_app.c`、KK_UI 与 KK_OLED 图形核心被编译到宿主上，对着一个记录驱动本会做出的
页/列写入的影子屏：真实的接口画出了 **0 个像素、发出了 0 字节**，而在同一套装置里一次直接
的文本渲染画出了 156。把那一个局部变量改到文件作用域，就让同一套装置渲染出了 MAIN MENU ——
在 8 个分页行中的 7 个上点亮 2114 个像素。那就是 `tests/host/test_ui_frame.c`，现在是一项
永久的回归测试。

跑很多帧而不只是一帧，也会走出那片死掉的内存：在宿主上它二三十帧之后就段错误。在目标板上，
同样的读取是悄无声息的。

## 上游禁止猜测、因而仍然悬而未决的事项

`skills/kk-oled-port/SKILL.md` 点名了本工程的这些确切未知项，说它们不得从参考驱动或通用模块
默认值填入，包括 CH1116-vs-SSD1306、`0x3C`-vs-`0x3D`、列偏移是 0 还是 2，以及"任何通用初始化
表"，并指出一次 I2C 扫描只能证明某个地址应答了。

据此，`App/display/oled_bus.c` 携带**三份完整的候选配置档**，
由 [HARDWARE_TEST_PLAN.zh-CN.md](HARDWARE_TEST_PLAN.zh-CN.md) 的 stage D/E 在台架上判定取舍。

**更新于 2026-09-19，来自第一块真实模块。** 那些未知项里有两个现在是由观察、而不是由猜测
关掉的：面板是 **SSD1306**（用户在模块上识别出来的，并且与下文一切都相符），而且它在
**7 位 `0x3C`**（HAL `0x78`）上应答，这正是地址扫描所发现的。一次整帧写入点亮了 128×64
玻璃上的每一个像素，所以所选配置档的电荷泵字节与显示开启字节是起作用的。

**仍然悬而未决、也不得靠推断关掉的。** 关于本模块的寻址已经没有剩下的了。真正仍未确定的
是其它候选配置档的行为：如果来的是一块不同的面板，那么 `0x3D`、带偏移 2 的 132 列 RAM，
或是另一种 COM 排布，都各自需要同样的台架证据，而一个全白帧给不出这种证据 —— 只有带边缘
的图案才行。

## 字体授权：MIT 许可证并不覆盖的那一件事

两个仓库都不携带字形数据，而被记录的生成方式使用的是一个在线服务，对它的输出 kk_oled 明确
说明受所选字体本身的许可证约束，而不是受 MIT 约束。把这类输出提交进公开仓库，本会是这里唯一
一个"随仓携带这些库"解决不了的许可证问题。

因此 `App/ui/ui_fonts.c` 中的 5×7 ASCII 字集是由 `tools/gen_oled_fonts.py` 为本工程自行编写
的，不涉及任何第三方字体。完全没有携带 CJK 字形，这也满足了任务书对大型中文字体表的禁止。

## 实际做过的验证

`tests/host/test_font_format.c` 把 `kk_oled_font.c` **未作修改**地针对生成的数组编译并解码：
78 条断言，覆盖头部解析、每一个可打印码点、自制的字形形状、十二对易混字符，以及对缺失码点的
回退。它发现了三个真实缺陷，而缺陷是靠审阅 C 数组看不出来的：一个过窄的 `advance` 字段、
一个让测试首版空洞通过的 off-by-one，以及 KK_OLED 的"无尾随间隔"宽度规则。

其余关于 UI 的一切 —— 布局、动画、焦点、居中 —— **仅通过编译验证**，直到 2026-09-19
第一块真实面板让这个问题变得具体。自那以后有两件事变了：

1. `tests/host/test_ui_frame.c` 不加改动地编译出货的 `ui_app.c`、KK_UI 与 KK_OLED 图形
   核心，只把 I2C 驱动换成一个影子屏 —— 它记录驱动本会执行的页/列写入 —— 并断言有一个
   真实场景到达了总线：MAIN MENU，最低要求是点亮 200 多个像素、跨好几个分页行，外加再
   60 帧，它们既不能崩溃也不能破坏那个描述符。它就是上面那个生命周期缺陷的守卫，而它正是
   通过把 0 个像素变成 2114 个像素来证明修复有效的。
2. 面板本身如今已经在硬件上回答了若干问题：PB6/PB7 上 400 kHz 的 I2C1、7 位 `0x3C`
   上的一个 ACK、SSD1306 初始化序列被接受，以及一次整帧写入点亮 128×64 模块上的每一个
   像素。见 [HARDWARE_TEST_PLAN.zh-CN.md](HARDWARE_TEST_PLAN.zh-CN.md) 的阶段 D 与 E。

**尚未在硬件上见到的：** 除 MAIN 菜单之外的每一页 —— ECG 波形、BODY TEMP、STATUS、
DATE & TIME、SETTINGS 与 ABOUT —— 外加按键导航与动画。宿主渲染是 `HOST VERIFIED`，那是
另一种主张。这块板子在 2026-09-19、生命周期修复之后确实确认的东西是菜单本身：文字居中、
没有水平偏移、没有行序错乱，而这也正是为本模块关掉列偏移与 COM 排布这两个问题的那次测量。
